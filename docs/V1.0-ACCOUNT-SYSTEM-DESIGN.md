# Lumi v1.0 账号系统 · 方案设计

> 文档版本：v1.0 草案
> 日期：2026-07-31
> 状态：Phase 1 已上线验证（2026-07-31）；Phase 2（E2EE 同步）已实现 + 真机验证通过（2026-08-01）；Phase 3（Plus 权益 + 支付）已实现 + **PayPal 沙箱全链路真机验证通过**（2026-08-01，v0.6.0）；Phase 4（伴侣加密共享）**已实现并随 v0.8.0 发布**（2026-08-03）
> 配套文档：`docs/ROADMAP.md`、`docs/PRICING-STRATEGY.md`

## 0. 结论摘要

仓库里**已经有一套相当完整的账号脚手架**（OAuth 端点、D1 数据层、客户端 store、部署配置都在），且 **Phase 1 已于 2026-07-31 上线验证**——Google OAuth 登录 / 登出 / 注销 / 删除后重注册全链路跑通。**D1 数据库表已通过迁移创建**（注意 `users` 表因历史 schema 缺 `apple_id` 列，新增 `0002_add_apple_id.sql` 补列——`CREATE TABLE IF NOT EXISTS` 对旧表不生效，CI 的迁移步是 `continue-on-error` 不会自动执行新迁移，需手动 `wrangler d1 migrations apply lumi-db --remote`）。

v1.0 账号系统的本质不是"登录按钮"，而是 **「登录 + 端到端加密同步 + Plus 权益门控」三件套**。按"先跑通账号、再上同步、最后接支付"的顺序分四个阶段落地，并且严格遵循定价红线：**只做加法，绝不回收任何 Free 功能**。

## 2. 关键缺口（必须补的）

### 缺口①：D1 建表迁移（最大阻断项，P0）
- 现状：`functions/utils/db.ts` 与 `session.ts` 直接 `SELECT/INSERT INTO users/sessions`，但**没有任何建表语句**，也没有迁移机制。D1 是空库时登录必 500。
- 方案：引入官方 **`wrangler d1 migrations`** 机制。
  - 新增 `migrations/0001_init.sql`：
    ```sql
    CREATE TABLE IF NOT EXISTS users (
      id TEXT PRIMARY KEY,
      google_id TEXT UNIQUE,
      apple_id TEXT UNIQUE,
      email TEXT NOT NULL,
      name TEXT,
      picture TEXT,
      created_at INTEGER NOT NULL,
      last_login_at INTEGER NOT NULL,
      CHECK (google_id IS NOT NULL OR apple_id IS NOT NULL)
    );
    CREATE TABLE IF NOT EXISTS sessions (
      id TEXT PRIMARY KEY,
      user_id TEXT NOT NULL REFERENCES users(id),
      expires_at INTEGER NOT NULL,
      created_at INTEGER NOT NULL
    );
    CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions(user_id);
    ```
  - CI（deploy.yml）在 `wrangler pages deploy` 前加一步：`npx wrangler d1 migrations apply lumi-db --remote --env production`（用 `CLOUDFLARE_API_TOKEN`）。
  - **本地开发**：`wrangler d1 migrations apply lumi-db --local` + `wrangler pages dev`。

### 缺口②：E2EE 同步层（账号的真正价值，P0 for Plus）
- **实现决策（2026-08-01，已与用户拍板）**：采用**对称 vault 方案**，取代本段原描述的 Ed25519 非对称方案。理由：单用户同步场景下两者安全性等价，对称方案更简洁、WebCrypto 原生支持好、实现更稳。具体见下方「对称 vault 方案」与 Phase 2 落地记录。
- 现状：无任何同步端点。本地数据在 IndexedDB（per-device），登录后没有"把我的数据放云端"的通道。
- 方案（端到端加密，密钥不出端）：
  1. **密钥生成**（客户端 `WebCrypto`）：每账号一对 Curve25519/Ed25519 密钥；用用户 passphrase 经 `PBKDF2`（或 Argon2id）派生对称密钥加密私钥，服务端**只存私钥密文 + 公钥**。
  2. **数据封装**：每条本地记录序列化为加密 blob（AES-GCM），附 `record_id` + `updated_at` + `hmac`。
  3. **存储选型（已定：R2）**：同步 blob 存 **R2**（二进制对象，避免 D1 单值/行大小限制），`meta` 索引放 D1 的 `sync_meta` 表（见 §4）。需在 `wrangler.toml` 加 R2 bucket binding，`deploy.yml` 注入 `R2_BUCKET`；`functions/api/sync.ts` 经 `env.BUCKET.put/get` 读写 blob。
  4. **端点**（新增 `functions/api/sync.ts`）：
     - `PUT /api/sync` 上传增量加密 blob（按 `updated_at` last-write-wins 解决冲突，直接覆盖 R2 上旧 blob + 更新 `sync_meta`）
     - `GET /api/sync?since=` 拉取增量
     - `GET /api/sync/snapshot` 全量（换设备首登）
  5. **冲突策略（已定：LWW per record）**：单用户多设备场景下，以 `updated_at` 大的版本为准覆盖，不做字段级合并 / 不做 CRDT。理由：个人健康数据单用户写入、并发编辑同一记录概率极低，LWW 实现简单、可审计、无合并语义歧义；若未来要支持伴侣共享（Phase 4）再评估字段级合并。
  6. **紧急恢复码（已定：先做 recovery codes）**：passphrase 是解密私钥的唯一口令，遗忘 = 云端数据不可读。提供一次性恢复码作为兜底——首次生成密钥时服务端下发 N 个随机恢复码（明文仅展示一次，`code_hash` 入库），用户在 Settings 可见/可重新生成；重置流程：校验身份（已登录会话或邮箱验证）+ 输入任一未用恢复码 → 清除旧 `key_backup` 并引导重设 passphrase，旧同步 blob 因无法解密而丢弃（明确告知用户）。**不做 escrow / 密钥分片**（成本与信任风险高，与"密钥不出端"原则冲突）。

### 缺口③：Plus 权益 / 订阅门控（变现前提，P1）✅ 已实现（2026-07-31）
- 现状：无任何"用户是否付费"的判断。`PRICING-STRATEGY.md` 定义 Free/Plus/Founder 三档，但代码无对应字段。
- 方案：
  - `subscriptions` 表：`user_id`、`plan`(`free`/`plus`/`founder`)、`expires_at`、`provider`、`provider_sub_id`（`provider` 取值：`paypal` | `code` | `null`）。
  - `GET /api/entitlement` 返回 `{plan, expiresAt}`，客户端据此解锁 Plus 功能（同步/共享/AI）。
  - **支付**：海外用 **PayPal**（`functions/api/billing/webhook.ts` 用官方 `verify-webhook-signature` 端点验签，避免手搓 CRC32/HMAC）——一次性订单用 **Orders API**（Founder 终身 ¥98 等值美元）、订阅用 **Subscriptions API**（Plus 年付），Webhook（`PAYMENT.CAPTURE.COMPLETED` / `BILLING.SUBSCRIPTION.*`）幂等写 `subscriptions`；国内 v1.0 用**激活码/手动激活**过渡（微信/支付宝接入较重，放 v1.x）。`PAYPAL_MODE=sandbox|live` 切换沙箱/生产，未配置 `PAYPAL_*` secret 时端点返回 503。
  - 门控原则：Free 用户永远可用 v0.5 全部功能；Plus 仅在"设置"低调入口展示，绝不弹 Nagware（红线）。
  - **PayPal 落地要点**：
    - 环境变量：`PAYPAL_CLIENT_ID` / `PAYPAL_CLIENT_SECRET`（secret），`PAYPAL_MODE=sandbox|live`（沙箱先测）。
    - 一次性（Founder）：前端创建订单 → `POST /v2/checkout/orders` → 用户 approve → `POST /v2/checkout/orders/{id}/capture` → webhook `PAYMENT.CAPTURE.COMPLETED` 写 `plan=founder`、`expires_at=NULL`（终身）。
    - 订阅（Plus）：先建 **Plan**（月/年两档）→ `POST /v1/billing/subscriptions` → 用户 approve → webhook `BILLING.SUBSCRIPTION.ACTIVATED` 写 `plan=plus`、`expires_at`；`CANCELLED`/`SUSPENDED`/`PAYMENT.FAILED` 置过期。
    - 金额：海外以 USD 计价（Plus ≈ $19.99/年，Founder ≈ 等值 $），与国内 ¥ 档通过地区分流。
    - 幂等：`provider_sub_id` 存订单/订阅 ID，webhook 重复投递不重复开通。

### 缺口④：安全与合规加固（P1）
- **OAuth PKCE**：当前仅 `state` 防 CSRF，补 `code_verifier`/`code_challenge`（公开客户端最佳实践）。
- **速率限制**：登录/回调加简单计数器（D1 或 KV），防爆破。
- **账号注销 + 数据导出**：`DELETE /api/account` 级联删 `users/sessions/sync_blobs`；配合已有 JSON 导出扩展为"导出云端数据"。
- **清理 refresh_token 误用**：`login.ts` 里 `access_type=offline`+`prompt=consent` 换取了 refresh_token 却从不存储/使用（我们用自有 session，不需要它）——删掉以减小攻击面。
- **共享类型**：`functions/utils/*` 里每个文件都重复声明 `D1Database`/`PagesFunctionContext` 接口——抽成 `functions/utils/types.ts`，降低维护风险。

### 缺口⑤（新增）：Apple OAuth 接入（iOS PWA 上架硬要求，P0 for 上架）
- 现状：`functions/auth/*` 只有 Google 端点；Apple 登录完全缺失。iOS PWA 若走 App Store 上架，Apple 审核指南要求提供「Sign in with Apple」作为等价登录选项，缺 Apple 登录会被拒审。
- 方案（Sign in with Apple，authorization code flow）：
  1. **Apple 开发者配置**：Service ID（client_id）+ 私有密钥 `AuthKey_*.p8`（Key ID + Team ID）；用 p8 生成 **client_secret（JWT，有效期 ≤6 个月，需定时轮换）**。
  2. **新增端点**：`functions/auth/apple-login.ts`（跳 `https://appleid.apple.com/auth/authorize`，带 `response_type=code id_token`、`scope=name email`、`state`+PKCE）→ `functions/auth/apple-callback.ts`（用 Apple 公钥 JWKS 验 `id_token`，或 code 换 token 后取 user；`upsertUser` by `apple_id`）。
  3. **数据模型**：`users` 表新增 `apple_id TEXT UNIQUE`（可空），原 `google_id` 改为可空（见 §2 缺口①迁移）；`db.ts` 加 `findUserByAppleId`/`upsertUserApple`。一条记录可只有 google_id 或只有 apple_id（CHECK 至少一个非空）。
  4. **隐私兼容**：Sign in with Apple 支持「隐藏我的邮件」——`email` 会是 `@privaterelay.appleid.com` 的 relay 地址；首次授权才返回 `name`，后续为空。代码需兼容 `name=null`、`email=relay`。
  5. **前端**：Settings 登录区加「使用 Apple 登录」按钮（`Apple` 图标）；PWA 任意浏览器可见（Apple 登录是上架硬要求，不限于 Safari）。
  6. **配置**：`wrangler.toml` 加 secret——`APPLE_CLIENT_ID`/`APPLE_TEAM_ID`/`APPLE_KEY_ID`/`APPLE_P8`（私钥内容）/`APPLE_REDIRECT_URI`；`deploy.yml` 注入。
- 与 Google 端点的关系：两个 provider 共用 `callback` 之后的 `upsertUser`/`createSession`/`种 cookie` 逻辑，建议抽公共 `completeOAuthLogin(user)` 避免重复。

## 4. 数据模型（目标态，增量补充）

在现有 `users`/`sessions` 之上新增：

```sql
-- Plus 订阅
CREATE TABLE subscriptions (
  user_id TEXT PRIMARY KEY REFERENCES users(id),
  plan TEXT NOT NULL,            -- free | plus | founder
  provider TEXT,                 -- paypal | code | null
  provider_sub_id TEXT,
  expires_at INTEGER,
  created_at INTEGER NOT NULL
);

-- 端到端加密同步（元数据索引放 D1，密文放 R2）
CREATE TABLE sync_meta (
  user_id TEXT NOT NULL REFERENCES users(id),
  record_id TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  blob_ref TEXT NOT NULL,        -- R2 key
  hmac TEXT NOT NULL,
  PRIMARY KEY (user_id, record_id)
);

-- 加密私钥备份（passphrase 加密后存）
CREATE TABLE key_backup (
  user_id TEXT PRIMARY KEY REFERENCES users(id),
  wrapped_private_key TEXT NOT NULL,
  salt TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

-- 紧急恢复码（passphrase 遗忘兜底；hash 后存储，一次性使用）
CREATE TABLE recovery_codes (
  user_id TEXT NOT NULL REFERENCES users(id),
  code_hash TEXT NOT NULL,        -- Argon2id/SHA-256 hash，非明文
  used_at INTEGER,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, code_hash)
);
```

## 6. 与定价红线的咬合

- **本地免费功能永不动**：v0.5 全部功能（趋势/围绝经期/BBT/科普/PDF/对比度）对任何用户可用。
- **Plus = 同步 + 共享 + AI**：这三项是后端功能，天然适合做付费墙，不触及 Free 核心。
- **日落承诺可落地**：因数据 E2EE + 可 JSON/R2 导出，停服前可开源同步服务或发纯本地终版，已购用户核心功能不丢失。

## 7. 风险与缓解

| 风险 | 缓解 |
|------|------|
| D1 冷启动延迟影响登录体验 | 会话 30 天长效；`me` 端点加缓存头（no-store 但可边缘缓存） |
| 同步 blob 被篡改 | 每条带 HMAC，客户端校验；服务端只当 opaque blob |
| 误删云端数据 | 注销走二次确认 + 软删除宽限期（7 天可恢复） |
| PayPal/webhook 重放（PAYMENT.CAPTURE.COMPLETED / BILLING.SUBSCRIPTION.ACTIVATED 等） | 用 `provider_sub_id`（订单 ID / 订阅 ID）幂等处理；订阅类事件需处理 `CANCELLED`/`SUSPENDED` 以正确过期 Plus |
| 密钥丢失 = 数据永久不可读 | ④ 恢复码机制（已定）：首次生成密钥下发一次性恢复码兜底；passphrase 仍为主路径，明确告知"无恢复码且遗忘 passphrase 则数据不可读" |
